# FreeMarkdown 拖拽问题调查报告

调查时间：2026-09-18
调查对象：Windows 上「从资源管理器拖文件进应用」与「应用内拖标签排序/分屏」两个功能互相冲突、长期无法同时工作的问题。

---

## 0. 一句话结论

1. **两个功能现在都能工作**：真机鼠标实测通过（拖拽标签排序、合并、换位分屏均成功，全程无 🚫 光标）；
   "拖一下就丢文档""点什么都打不开"这两个严重 bug 的根因也已定位并修复（见 4.2 节）。
2. **「怎么改都不行」的直接原因已查明**：前端 dev server（vite，1420 端口）在 07:44 崩溃退出，而应用窗口里一直跑着崩溃前加载的旧代码——此后所有修复从未被加载执行过。这不是错觉，是事实。
3. **12 小时反复的根因是 Tauri/wry 层面一个结构性冲突**：一个窗口内，"原生文件拖放能拿到真实路径"与"应用内 HTML5 拖拽正常"在默认配置下互斥。下面附源码级证据。
4. **「拖一下就丢文档」是 dockview 的一个 API 陷阱**：对自身分组调用 `moveTo({position: 边缘})` 会抛 `Invalid grid element` 并把分组视图从 DOM 摘掉，网格进入不可用状态（文档消失、之后什么都打不开）。已改为只用可靠路径，并加了损坏自愈（见 4.2 节）。

## 2. 冲突的机理（源码级证据）

需求本身要求两条互相排斥的链路：

- **从资源管理器拖文件进来**：需要文件的**真实路径**。WebView2 的 DOM `File` 对象**不含路径**，所以必须由宿主（Rust/原生层）经 `CF_HDROP` 取出路径。
- **应用内拖标签排序/分屏**：需要页面能收到 **HTML5 拖拽事件**（dockview 的原生拖拽基于 HTML5 DnD）。

在 Windows + WebView2 上，Tauri 的 `dragDropEnabled: true` 会让 wry 做以下动作（行号为对应 crate 源码）：

**① `tauri-runtime-wry-2.11.4/src/lib.rs:4862`**
```rust
if webview_attributes.drag_drop_handler_enabled {
    webview_builder = webview_builder.with_drag_drop_handler(move |event| { ... });
}
```

**② `wry-0.55.1/src/webview2/mod.rs`（约 150–160 行）**：装上 drop handler 后，wry 随即：
```rust
let drag_drop_controller = drop_handler.map(|handler| {
    // Disable file drops, so our handler can capture it
    let _ = controller
        .cast::<ICoreWebView2Controller4>()
        .and_then(|c| c.SetAllowExternalDrop(false));   // ← 第 155 行
    DragDropController::new(hwnd, handler)
});
```
`DragDropController::new` 会 `EnumChildWindows` 枚举 WebView2 的所有子窗口，对每个窗口执行
`RevokeDragDrop(hwnd)` + `RegisterDragDrop(hwnd, wry 自己的 IDropTarget)`
——**把 WebView2 自己的 OLE 拖放目标整个替换掉**。

**③ `wry-0.55.1/src/webview2/drag_drop.rs`（`impl IDropTarget_Impl`，第 158 行起）**
wry 的 IDropTarget **只认 `CF_HDROP`（文件拖放）**：

```rust
fn DragEnter(...) -> Result<()> {
    let hdrop = DragDropTarget::iterate_filenames(pDataObj, |path| paths.push(path));
    let enter_is_valid = hdrop.is_some();
    if !enter_is_valid { return Ok(()); }        // ← 非文件拖拽：直接返回，不改 *pdwEffect
    ...
    *pdwEffect = cursor_effect;                  // 只有文件拖放才给 DROPEFFECT_COPY
}

fn DragOver(...) -> Result<()> {
    ...
    *pdwEffect = *self.cursor_effect.get();      // 非文件拖拽 → DROPEFFECT_NONE
}

fn Drop(...) -> Result<()> {
    if unsafe { *self.enter_is_valid.get() } {   // false → 什么都不做，Drop 被吞掉
        ...
    }
}
```

**推论（已被实测证实）：**

- `dragDropEnabled: true` 时，应用内的 HTML5 拖拽（dockview 标签拖拽）会命中 wry 的这个 IDropTarget：`DragEnter` 取不到 `CF_HDROP` → `*pdwEffect` 保持 `DROPEFFECT_NONE` → **OS 光标显示 🚫**；并且 `Drop` 被 wry 吞掉 → **页面收不到 `drop` 事件** → 拖拽必然无效。
- `dragDropEnabled: false` 时，wry 不注册 handler，应用内 HTML5 拖拽恢复正常，但外部文件拖放拿不到真实路径（DOM `File` 无 path）。

这就是"二选一"的结构性来源。

## 3. 已尝试的三条路线

### 路线 A（当前采用，已验证可用）

保留 `dragDropEnabled: true`（文件拖放走原生 `tauri://drag-drop` 事件，能拿到路径），
**应用内标签拖拽改为自研 Pointer Events 实现**：在 dockview 的 `onWillDragPanel` / `onWillDragGroup` 里调用
`event.nativeEvent.preventDefault()` 取消原生 HTML5 拖拽会话 —— **没有拖拽会话，就不会进入 OS 拖拽循环，也就不会有 🚫**。

实现位置：
- `src/components/useTabDrag.ts` —— Pointer Events 接管：`pointerdown` 命中标签后，位移超过 6px 进入拖拽，自绘 ghost 跟手 + 落点预览框；`pointerup` 时按落点执行 `moveTo`；Esc / `pointercancel` 取消。
- `src/lib/tabdrop.ts` —— 落点判定规则：落在标签上=排序到该位置；落在标签栏空白=追加到末尾；落在内容区中央=并入该分组；距分组边缘 < 24px=向该方向分屏。
- `src/components/DockHost.tsx` —— 接线 + dockview 配置。

### 路线 B（写好但未验证通过，建议专家确认）

关闭 `dragDropEnabled`（即让 WebView2 自己的 `AllowExternalDrop` 保持默认 true），让 **DOM 层收到外部文件 drop**（`dataTransfer.files`），再用 WebView2 官方接口
`window.chrome.webview.postMessageWithAdditionalObjects(message, fileObjects)` →
宿主侧 `ICoreWebView2WebMessageReceivedEventArgs2::AdditionalObjects` → `ICoreWebView2File::Path` 取真实路径。
桥接代码已实现：`src-tauri/src/filedrop.rs`（Rust 侧）+ `src/lib/filedrop.ts`（前端侧）。

**这条路线上次"拖不进、无反应"，很可能是因为缺少 `dragover` 上的 `preventDefault`**（HTML5 规则：不 preventDefault `dragover`，就永远不会触发 `drop`）。**未做验证。**

### 路线 C（不可行）

两条链路都要、又不动任何一边 —— 由第 2 节的机理可知不可行。

## 4. 路线 A 的实测证据

测试方式：应用运行中（Tauri dev + WebView2 远程调试端口 9223），
用 CDP 合成鼠标事件做功能验证，再用**真实鼠标**做最终验收（真实鼠标会进入 OS 拖拽循环，是唯一能证明"无 🚫"的方式）。

| 测试项 | 方式 | 结果 |
|---|---|---|
| 拖到另一窗格**中央** | CDP 合成鼠标 | 两个窗格合并为 1 组 2 标签 ✔ |
| 拖到另一窗格**左边缘** | CDP 合成鼠标 | 左右窗格互换 ✔ |
| 同组内拖到另一个标签上（排序） | CDP 合成鼠标 | 标签顺序翻转 ✔ |
| 拖到同一窗格右边缘（单面板组） | CDP 合成鼠标 | 视觉等价，无可见变化（预期行为） |
| **真实鼠标拖拽** | 真实鼠标 | 拖拽中 ghost + 预览框正常显示；**全程无 🚫**；松手后窗格成功互换 ✔ |

**真机那次的事件级证据**（页面内注入记录器读出）：

- `dragstart` 触发后，`drag` / `dragover` / `drop` / `dragend` **一次都没有出现**
  → 原生 HTML5 拖拽会话在 `dragstart` 阶段就被 `preventDefault` 取消了，OS 拖拽循环从未启动 → 不可能出现 🚫。
- `pointermove` 连续 50 次、`pointerup` 在 (965, 528) 正常触发 → 指针链路完整。
- 松手后 DOM 标签顺序变为 `验收样例.md x=0`、`第2章_样章草稿.md x=960`（互换成功）。

对照实验（关键）：在**旧代码**（未注册 `preventDefault`）下，同样的合成拖拽会出现 12 次 `drag`、6 次 `dragenter`、9 次 `dragover`、1 次 `drop` —— 原生会话正常启动并自己完成了分屏（说明原生路径本身没坏，坏的是它在真实 OS 拖拽循环下会被 wry 的 IDropTarget 判成 NONE）。

## 4.1 本轮另外修复的两个问题（均已验证）

**问题 1：拖拽结束后残留 ghost / 预览框。**
原因：松手时指针已经在窗口外，`pointerup` 没送达页面，清理逻辑没机会执行，覆盖层就永久留在 DOM 上（截图里"合并在一个组了、右边还挂着一个白框"就是这个）。
修复（`src/components/useTabDrag.ts`）：
- 拖拽开始时对标签调用 `setPointerCapture(pointerId)`，松手即使发生在窗口外也能收到 `pointerup`；
- 监听改到捕获阶段（避免被其它组件 `stopPropagation` 吞掉）；
- 补三重兜底：拖拽中收到 `buttons === 0` 的 `pointermove`（说明按钮早松了）、`window.blur`、`dragend`、组件卸载，任一路径都会清理覆盖层；
- 每次新拖拽开始前先清一次残留。
验证：模拟"松手事件丢失"（只发一个按钮已松开的移动事件）→ 覆盖层归零 ✔；在**视口外**松手（x=-40, y=-40）→ `pointerup` 仍送达、覆盖层归零且不会误触发移动 ✔。

**问题 2：上下分屏判定只能拖到极低位置才生效。**
原因：原判定是"把到四边的距离各自除以宽/高后比大小"，宽窗格（1920×965）下竖直方向的比值天然吃亏（`dy/965` 永远大于 `dx/1920` 的量级），左右两边几乎总是赢；而且边缘带宽只有固定 24px，必须贴到最边上。
修复（`src/lib/tabdrop.ts`）：改为**与 dockview 原生 overlay 完全一致的规则** —— 带宽 = 内容区尺寸的 **20%**（dockview `DEFAULT_ACTIVATION_SIZE = { value: 20, type: 'percentage' }`），优先级固定为 `left → right → top → bottom`，都不沾边才是 center；坐标基准改用「内容区」（`.dv-content-container`，不含标签栏），与原生 overlay 一致。
验证（确定性断言，`scripts/zone-assert-probe.mjs`）：
- 拖到目标窗格内容区中央 → 合并为 1 个分组 **PASS**；
- 拖到内容区顶边带（高度 10% 处）→ 上下堆叠分屏，且被拖面板位于上方 **PASS**；
- 拖到底边带正中 → 上下堆叠（1920×482 / 1920×483）**PASS**。

## 4.2 严重 bug：「拖一下就丢文档」的根因与修复（已定位并验证）

**现象**：上下分屏时，把上面窗格的文档标签往右拖，文档直接消失；此后"点什么都打不开"。

**根因（源码 + 实测双重确认）**：`panel.api.moveTo({ group: <面板自己所在的分组>, position: 'left'|'right'|'top'|'bottom' })`
在 dockview 4.13.1 上会抛 `Invalid grid element`，并且可能**中途把分组视图从 DOM 上摘掉**。
dockview 靠 DOM 反推网格位置（`getGridLocation()` 走 `element.parentElement` 链，见
`dockview-core.esm.js:2204-2227`），元素一旦脱离 DOM：

- 该面板之后的 `moveTo` 会把面板摘出分组却再也放不回去 → **文档消失**；
- `addPanel` 静默失效（不抛错也不加面板）→ **点什么都打不开**；
- 残留的 0 面板空分组还会渲染成一层 `.dv-groupview` 盖在别的分组上，挡住点击。

**实测矩阵**（干净页面，直接调 API）：

| 调用 | 结果 |
|---|---|
| 单面板分组 + `moveTo(自身组, 'right')` | ok（无变化） |
| 单面板分组 + `moveTo(自身组, 'bottom')` | **抛错并让 domGroups 归零（网格损坏）** |
| 双面板分组 + `moveTo(自身组, 'right')` | **抛错** |
| 双面板分组 + `moveTo(自身组, 'bottom')` | **抛错** |

**修复（4 处）**

1. **永不发出同组边缘 `moveTo`**（`src/lib/tabdrop.ts`）：
   单面板分组直接保持原位（本来就无处分屏）；多面板分组改为
   「`addGroup({referenceGroup, direction})` 新建相邻分组 → `moveTo(新分组, 'center')`」，
   只使用实测可靠的路径，且两步必须在同一个同步块内完成（否则会被空分组清扫摘掉）。
   跨组边缘仍走原来的 `moveTo`（实测正常）。
2. **损坏检测 + 就地修复**（`src/lib/store.ts` + `src/components/useTabDrag.ts`）：
   `gridBroken()` 判定「有分组、但其元素已 `isConnected === false`」；
   `repairGrid()` 把脱离的视图回填进 `.dv-view-container`（实测回填后 `addPanel`/`moveTo` 全部恢复正常）。
   打开文档前、拖拽开始前都会先检测/修复。（注意：**不能**用"销毁并重建 dockview 实例"来恢复——
   实测销毁损坏实例时它自己的 `dispose()` 会 `removeChild` 失败并抛错，把 React 子树整个带崩。）
3. **移动后校验面板存活**（`useTabDrag.ts`）：`moveTo` 之后若面板不在 `api.panels` 里，立即按路径重新打开（内部会按需修复网格）。
4. **空分组清扫**（`DockHost.tsx`）：布局变化 400ms 后清掉 0 面板的 grid 分组（空分组无内容可丢），
   避免它盖住界面、阻塞点击、破坏落点判定。

**同时修掉的两个隐患**

- **落点分组映射**：原来用「DOM 中 `.dv-groupview` 的序号 → `api.groups[序号]`」，
  一旦有空分组两者顺序就不一致，会把移动目标指到错误分组（甚至浮动分组）上。
  改为按元素身份查找：`api.groups.find(g => g.element === gv)`；空分组不作为落点。
- **路径归一化**（`store.ts`）：面板 id 由路径拼出，`J:/a/b.md` 与 `J:\a\b.md` 会被当成两个文档
  （重复标签）。新增 `normalizePath()`：Windows 盘符路径统一转反斜杠。

**验证**（`scripts/final-regress.mjs`，全部通过）

| 用例 | 结果 |
|---|---|
| ① 同组拖到自身右边缘 → 左右分屏 | PASS（修复前：网格损坏 + 后续丢文档） |
| ② 同组拖到底边带 → 上下分屏 | PASS |
| ③ 跨组拖到另一组左边缘 → 换位 | PASS |
| ④ 拖到另一组中央 → 合并为 1 组 | PASS |
| ⑤ 同组内标签排序 | PASS |
| 用户场景：上下分屏后拖上窗格往右（三个高度位置） | PASS ×3（`脱节=false`，面板不丢） |
| 损坏态自愈：摘掉分组视图后打开文档 | PASS（回填修复，不换实例、不崩溃） |

## 5. 还没解决 / 需要专家判断的点

1. **路线 B 是否可行**（最想知道）：
   在 `SetAllowExternalDrop(true)`（即 `dragDropEnabled: false`）下，从资源管理器拖文件进 WebView2，**DOM 究竟能不能收到 drop 事件（`dataTransfer.files` 非空）**？
   - 若能：B 是最优解 —— 应用内拖拽恢复 dockview 原生全功能（排序、分屏、浮动组、跨实例拖拽全部回来），文件拖放用 `postMessageWithAdditionalObjects` 取真实路径，不再需要自研指针拖拽。
   - 若不能：只能留在路线 A。

2. **路线 A 的两个功能缺口**（因为 DOM 层收不到外部 drop，只能靠原生事件里的坐标自己实现）：
   - 「文件拖到**哪个窗格**就在哪个窗格打开」：原生 `tauri://drag-drop` 事件带 `position`，可以据此对窗格做命中判定；当前代码忽略了 `position`，文件一律开在活动窗格。
   - 「文件拖到窗格**边缘**自动分屏」：同上，需要自己按坐标算边缘区域。

3. **路线 A 的能力边界**（原生 HTML5 拖拽被取消带来的副作用）：
   - dockview 原生支持的"拖到标签栏空白处追加"、"Shift+拖拽变浮动组"、"跨 dockview 实例拖拽"目前不可用；
   - 我们的指针实现只覆盖：排序、并入、四向边缘分屏。
   - 需要确认这些能力是否在需求范围内（若需要浮动组等，路线 B 的价值会更大）。

4. **多显示器 / 高 DPI 下指针坐标**：本次验证环境 DPR = 1；高 DPI（125%/150%）下自绘 ghost 与落点判定用的是 CSS 像素，理论上无影响，但未实测。

## 6. 附：「怎么改都不行」是如何发生的（流程问题）

- 前端 dev server（vite，1420 端口）在 **07:44 崩溃退出**（`pnpm dev` 日志结尾：`ELIFECYCLE Command failed with exit code 1`）。
- 应用是 Tauri dev 模式，页面早已加载完成；**dev server 挂掉不会让已加载的页面报错**，它会继续运行崩溃前那份 bundle。
- 于是 07:44 之后的所有代码修改（包括整条路线 A 的实现）**从未进入过运行中的应用窗口**。人在屏幕上看到的自然永远是一模一样的行为。

**建议加两道保险：**
1. 应用启动时把构建时间戳（或 git hash）打印到控制台 / 设置页"关于"，一眼可判断跑的是哪一版；
2. 验收前先 `curl 127.0.0.1:1420` 确认 dev server 存活，再做人工验证。
