## 实现要点

### 双向联动（方案 §4.6）

- **单一坐标系 = 源码行号**。预览块带 `data-start`/`data-end`（comrak `data-sourcepos`），滚动任何一侧都先换算成行号再驱动另一侧。
- **编辑器定位不用 `EditorView.scrollIntoView`**：目标已在视口内时它直接不动，联动会表现为"另一侧只挪一点点"。
  改为按 `lineBlockAt` 的真实几何算绝对 `scrollTop`（`scrollTop = 块顶 - 滚动容器屏幕顶 - 边距`）。
  踩过的坑：`BlockInfo.top` / `view.documentTop` 是**屏幕坐标**，当成文档坐标会算出天文数字再被夹住。
- **同步锁 + 尾随补跑**（`SyncLock`）：一侧驱动另一侧时上 180ms 锁，防止互相拉动抖动；
  锁期内到达的事件记为 pending，锁过期后补跑最后一次，避免丢掉一串滚轮的最后一帧（实测会残留 2 个块的偏差）。
- **恢复后静默期**：冻结恢复时两侧快照位置可能本来就不完全一致，先静默 700ms，
  再以编辑器视口为准对齐预览。
- **预览只有在用户真实手势后才反向驱动编辑器**（`onPointerDown`/`onWheel` 置位），
  避免恢复过程中预览的程序化滚动把编辑器视口拽回顶部。
- **窗口化预览的按行跳转**：目标块在窗口外时没有 DOM，无法直接对齐。
  `alignPreviewToLine` 先按估算高度把窗口滚过去，再用「目标行 / 当前顶部行」线性外推逼近，
  目标块进窗口后精确对齐（2MB 文档实测：从文档 2% 位置逼近到目标块，两侧顶块一致）。

### 块级局部替换（方案 §4.2）

- 预览块以 `block.rev` 作 React key：未受影响的块在拼接时元素身份不变（S1：39/40 同一节点、0 重写）。
- `data-rev` 与 `innerHTML` 由注入器直接管理（版本比对，内容变了才重写）；
  行号平移只改 `data-start`/`data-end`，不触发 HTML 重写。

### 冻结恢复的视口坐标

- 快照里的滚动位置**不能现场读** `scrollDOM.scrollTop`：切标签时 dockview 先卸载面板，
  容器失去可滚动范围后浏览器把位置夹成 0，卸载清理读到的是 0（实测 2MB 文档 543,457px → 0，切回视口落回文档顶部）。
  改为在滚动回调里持续记录"最后可信读数"，且只在容器可见（`clientHeight > 0`、已连树）时记录。
- 恢复按「行号粗定位 → 像素精定位」：CM6 高度图测准前按行先滚到附近（行号不依赖长度估算），
  范围够了再写精确像素值；落位后 260ms 复查一次，防止行号路径的 settle 定时器或 CM6 的测量回合把位置挪回去
  （只按行对齐会差一个"部分可见块"，全量套件里实测偏 65px）。实测 543700 → 543700（0px）。

### 增强降级（方案 §4.2 硬规则 3）

- 打字期间新挂载的 mermaid/KaTeX 块保持源码态（`raw`），停手 320ms 后再补增强；
  补齐结果与整篇渲染一致（同一张图 viewBox 相同）。
- 含脚注定义 `[^id]:` 的文档整篇重渲染兜底：脚注编号依赖全文顺序，宁可多解析不可渲染错。

### 外部改动监听（方案 §4.7）

- Rust 侧 `notify` 常驻监听（`src-tauri/src/watch.rs`）：watch 父目录（重命名安全的做法）、
  80ms 去抖、事件带 `mtimeMs`，前端按路径 + mtime 过滤，自己写盘后 1500ms 内的事件不当作外部改动。
- 阅读面板：外部改动 → 按新 mtime 重读（LRU 以 (路径, mtime) 为键，天然失效）；
  编辑面板：干净缓冲直接重载，脏缓冲弹冲突横幅（覆盖 / 重新载入 / 另存为）。
- 许可：`notify` 8.2.0 为 **CC0-1.0**（公共领域），符合"只用宽松许可"的项目规则。

## 已知限制与取舍

1. **S2a 的四个方向用 1MB 夹具**：验收样例只有约 130 行，从 45% 起步时编辑器已贴住底部，
   向下滚轮完全不动（判定里的"被驱动侧没动"其实是被驱动方没得动）。1MB / 2.6 万行的文档
   四个方向都有充足余量，同时覆盖窗口化预览的联动；点击跳转（S2b/S2c）仍用小块夹具，
   保证视口内有完整可见的块可点。
2. **窗口化预览的远距离跳转是逼近式的**：靠估算高度 + 外推收敛，极端不均匀（大量图片/巨型表格）的文档
   可能需要更多轮；收敛失败的兜底是"停在最接近的已挂载块"，不会跳飞。
3. **脚注文档**退化为整篇重渲染（2MB 级有明显延迟），属已知取舍（与阶段 1 报告一致）。
4. **React 渲染上限**：预览的"实测高度修正"带重渲染上限（6 次 + rAF 节流），
   防止标签/图片的异步布局把渲染打成死循环（此前曾因无限测量循环触发
   "Maximum update depth exceeded" 导致整页空白）。
5. **`restoreScrollTop` 的重试上限**对超长文档仍可能不足（当前 6 帧 + 3s 时间预算），
   更极端的文档需要按行号重试更多轮。
6. **C8b / C9 的场景依赖**（探针使用说明）：这两项需要前面各项积累的布局现场
   （编辑窗格独立成组、保持渲染）。单独跑时请直接跑全套 `node scripts/edit-probe.mjs`；
   其中 C9 会强杀应用进程，固定最后执行。
7. **验收夹具不再就地改写**：两个探针会把仓库里的 `testdata/验收样例.md` 先拷到
   `testdata/out/` 再编辑（探针会真实键入并自动保存），避免把测试痕迹留进受版本控制的文件。
